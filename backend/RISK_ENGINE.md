# Phase 3：規則式風險引擎（RISK_ENGINE）

建立日期：2026-09-13
程式位置：`backend/app.py` 的 `SAFETY_RULES`、`PROXIMITY_RULES`、
`compute_rule_based_hazards()` 及其輔助函式（`_detected_probability`、
`_band_risk_level`、`_bbox_gap`）。

## 一、要解決的問題

Phase 3 之前，`risk_level`（低/中/高）完全由視覺語言模型（VLM）自由文字判斷，
沒有跟實際偵測到的違規項目掛勾，同一張圖重跑可能得到不同結果，也無法對使用者
解釋「為什麼是高風險」。這對一個要拿來做安全稽核紀錄的工具而言，可重現性與
可稽核性不足。

Phase 3 把 `risk_level` 改成完全由「最終偵測清單」用固定公式計算，VLM 只負責
場景描述與 YOLO 類別涵蓋不到的補充性隱患（不影響風險等級）。

## 二、核心公式

```
風險值 = 偵測危害機率 L (1~5) × 嚴重度 C (1~5)      範圍 1~25
風險值百分比 = 風險值 / 25 × 100
```

**命名刻意用「偵測危害機率」而不是「危害機率」**：後者容易被誤解成套用通用
職災統計算出來的真實事故機率；這裡的 L 只是「這次影像分析當下的證據強度」
（偵測信心值＋同類違規數量），跟真正的事故發生率是兩回事，用不同名稱避免
工具過度宣稱準確度。

### 偵測危害機率 L（動態，每次分析依偵測結果計算）

```
conf_component = 1 + (confidence - 0.5) / 0.5 × 4     # 0.5→1，1.0→5
count_bonus    = min(count - 1, 2)                     # 同類違規每多一筆 +1，上限 2
L = clip(round(conf_component) + count_bonus, 1, 5)
```

- `confidence` 是 YOLO 對這個偵測的信心值（0.5~1.0，因為 YOLO 呼叫時
  `conf=0.5` 為門檻）。信心值只代表「這個偵測是不是真的存在」，**不代表
  這件事有多危險**——那是嚴重度 C 的工作，兩者故意分開，避免邏輯混淆。
- `count` 是同一張圖裡同類別違規的數量（例如 3 個人都沒戴安全帽）。

### 嚴重度 C（固定值，依違規類別）

代表「如果這個違規是真的，後果多嚴重」，與偵測信心、數量無關。

### 風險等級門檻（風險值 1~25 → 低/中/高）

| 風險值 | 等級 |
|---|---|
| 16~25 | 高 |
| 9~15 | 中 |
| 1~8 | 低 |
| 0（沒有命中任何規則） | 低 |

這組門檻是經驗值（呼應使用者自己那套矩陣系統「min_score 是經驗值，可依
實際回饋調整」的做法），可依現場使用回饋調整 `RISK_LEVEL_THRESHOLDS`。

提示（避免雜訊）。這組門檻是保守的經驗值，不是嚴謹的三維量測，僅供參考。

## 四、VLM 的角色（Phase 3 後）

VLM（Ollama qwen3-vl）不再輸出 `risk_level`，`hazards` 也限定只能是「YOLO
偵測類別涵蓋不到、需要整體畫面判讀才看得出來」的補充性隱患（例如物料堆置
不穩定、通道阻塞、開口未加蓋、照明不足、天候影響）。這類 hazard 在最終結果
裡標記 `source: "narrative"`，其餘規則引擎欄位（n_code／regulation／
detected_probability 等）為 `null`，且不參與 risk_level 計算。

### PDF 匯出（quality tier）prompt 額外帶的法規引用清單（2026-09-13 新增）

`analyze_with_ollama()` 新增 `tier` 參數。只有 `tier == "quality"`（也就是
點擊「匯出 PDF 報告」時用 8B 模型重新分析那一次）才會在 prompt 裡多帶一段
「任務 3：法規引用」，把 `_build_regulation_reference_text()` 彙整出的、
**已逐字查證確認**的正式法規條文列給模型參考，讓 `recommendations` 的建議
文字視情況引用真實條號；一般網頁圖片分析／webcam 即時顯示（`tier ==
"fast"`）不加這段，維持原本較短的 prompt，避免拖慢即時回應。

這份清單只讀每條規則的 `confirmed_citation` 欄位（`SAFETY_RULES` /
`PROXIMITY_RULES` 裡新增的欄位，`None` 表示尚未查證，就不會被列進清單）——
故意跟給人看的 `regulation` 欄位分開存放，因為 `regulation` 常常是「已確認
部分」跟「還待確認部分」混在同一句話裡（例如 Person–Machinery 這條，吊掛
物下方已查到條文、操作半徑還沒），如果直接把整句丟給模型當引用清單，模型
會連「待確認」的字樣一起學走、誤以為那也是可以引用的內容。`confirmed_citation`
只放可以放心引用的條文，prompt 裡也明講「絕對禁止引用清單以外的任何法規
名稱或條號」，避免模型自己編出一個看起來像的法條號碼。

截至 2026-09-13，唯一有 `confirmed_citation` 的是 `PROXIMITY_RULES` 裡
Person–Machinery 那條（見上方「距離類規則」表格的《職業安全衛生設施規則》
第92條、第153條）。之後只要把其他規則的 `confirmed_citation` 從 `None`
填成查證過的條文，這份清單會自動變長，不需要改 prompt 的寫法。

## 五、輸出格式

每個 hazard（不論來源）都是這個形狀：

```json
{
  "description": "偵測到 2 名人員未戴安全帽，有物體飛落擊中頭部之虞。",
  "severity": "high",
  "n_code": "N2",
  "hazard_name": "未戴安全帽",
  "regulation": "各工項查驗表列必要 PPE 項目（單一違規對應的確切法條號尚待人工確認）",
  "detected_probability": 5,
  "severity_score": 4,
  "risk_score": 20,
  "risk_percentage": 80,
  "informational": false,
  "source": "rule"
}
```

`AnalysisResult`（`/api/analyze`）與 `DetectResult`（`/api/detect`）都額外
帶有 `risk_score`（1~25）與 `risk_percentage`（0~100）兩個欄位。

## 六、已知限制／後續可做

- 沒有工項（工作類型）感知：同一套嚴重度不分模板作業／隧道工程／道路工程，
  但使用者的原始系統其實是依工項分群評分的。目前擴充功能沒有輸入「現在是
  哪種工項」的機制，暫不處理，先用同一套通用規則。
- 距離類規則的 2D 判斷本質上是粗略代理值，不能取代現場人員自行確認。
- 單一違規動作對應的確切法條號尚待人工確認（見上）。
- 嚴重度 C 的數值、風險等級門檻（16/9/1）都是初版經驗值，可依實際使用
  回饋在 `SAFETY_RULES` / `PROXIMITY_RULES` / `RISK_LEVEL_THRESHOLDS` 調整，
  不需要改動計算邏輯本身。
